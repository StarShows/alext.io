ALEXT.IO / LEARN

Learning to code should feel like building, not scrolling.

I built a full-stack, interactive learning environment that turns small JavaScript and web-engineering concepts into practice, immediate feedback, and progress you can actually keep.

Explore the app ↗

01 The problem

Most learning tools are good at explaining a concept, then leave you wondering whether you actually understand it. I wanted a tighter loop: learn one thing, try it, get feedback, and remember where you left off.

02 What I built

A browser-based learning lab with short lessons, JavaScript coding exercises, quizzes, contextual hints, an assessment flow, and a progress system with XP and review state. It is a real deployed app, not a static tutorial or a portfolio prototype.

03 The engineering decision

Keep the practice loop fast in the browser, but make progress durable on the server. The learning interface and exercise checks respond immediately; the Node.js application handles authenticated user state, and SQLite persists progress across sessions. The app runs under alext.io/learn on a Node.js-enabled Namecheap deployment.

The interesting part: this is a learning product with real state, real sessions, and an intentionally low-friction user experience, not just a set of exercises.

DISNEY / TITAN

The proof of concept was Airtable. The product was much bigger.

Titan began with an Airtable proof of concept for structured business-application data and attestation workflows. The full product evolved into a MERN platform with an AWS Bedrock AI layer, custom MCP interfaces, and DAG-orchestrated work.

Discuss the architecture ↗

01 The problem

An Airtable proof of concept is a useful way to prove an intake and data-attestation workflow. It becomes a constraint when the application needs to integrate large enterprise datasets, reconcile different source systems, and support richer user experiences and operational logic.

02 What I built

I worked across the full-stack architecture: React interfaces, Node.js and Express services, MongoDB-backed application behavior, and integration logic working with large volumes of Snowflake and ServiceNow data. The AI layer used Amazon Bedrock, custom Model Context Protocol (MCP) tooling, and directed acyclic graph (DAG) workflows to support multi-step processing.

03 The engineering decision

The shift was from a useful table-driven experiment to deliberately separated services. Data ingestion and mapping belong in API and processing layers; application state and workflows belong in the product; AI needs defined tool interfaces and explicit execution steps rather than an opaque chat window wired directly to enterprise records.

The story is about turning an early validation tool into an extensible engineering platform while keeping data integration, application workflows, and AI orchestration distinct.

HOAG / EPIC INTEGRATION

A scheduling experience is only as good as its EHR integration.

I worked on connected scheduling and secure medical-communication experiences for Hoag, integrating modern React / Next.js interfaces and MERN services with Epic through FHIR resources and Cloverleaf HL7 messaging workflows.

Discuss the integration ↗

01 The problem

A polished appointment UI means little if the clinical record cannot understand the appointment, patient context, or attached medical information. Healthcare systems use different integration contracts, and mistakes in identifiers or message routing matter far more than an ordinary form error.

02 What I built

I built features across a React / Next.js frontend and Node.js-based full-stack services for scheduling and secure clinical communication. The integration work connected Epic FHIR patient and scheduling context with HL7 message flows routed through Cloverleaf, including workflows around imaging appointments and clinical documents.

03 The engineering decision

Keep the user-facing experience separate from the clinical integration boundary. FHIR is useful for structured resource lookups and identity context; Cloverleaf handles HL7-style interoperability and downstream messaging. The application layer coordinates validation, API interactions, and safe handling of healthcare data without exposing clinical system details in the browser.

The technical challenge wasn't just building forms. It was making a modern application behave responsibly inside an existing medical integration ecosystem.
